TRANSMISSION 031

The Active Source-of-Truth
Gate

A site can have a green build and a working route and still be the wrong public body. This note says what was built to catch that, what it checks and does not, what happened in July when the difference showed up, and what is still a design.

July 2026, revised November 2026·Publication governance·Check and gap record·11 min read
Dated. The original was written on 1 July 2026 during a manual publication run. This revision describes the website repository as read on 10 November 2026: its checker script, its tests and its history. The live domain was not queried for this revision.
Revised 10 November 2026. The original described a five-organ gate, a twelve-point protocol, a set of failure labels and a Release Identity Controller as though they were a system. This revision separates them: one read-only checker exists; most of the twelve points are covered by its ten checks; two are not; the labels and the controller are designs. It adds the dated history from the repository, a drift model that uses the checker’s real names, and a list of what the checker cannot see. Interactive panels were added.
Correction, 10 November 2026. The June-July text said the gate "stops deployment, aliasing, public posting, and registry mutation until the gate passes". Nothing in the repository connects the checker to a deploy command. The checker is a read-only script that people run; the publication checklist in the repository’s instructions lists it as a step; the decision to deploy is the operator’s. The text also named failure labels (such as a stale lane or a live-ahead state). Those labels are not in the code. The checker reports named checks that pass or fail and says nothing about whether the live site is behind or ahead.
01

Publication is identity transfer

The idea, and the dated trail behind it

The idea in the original has held up. Writing the next page is not the hard part of publishing. The hard part is knowing that the page is being added to the same public body readers already see. A build can pass and a route can resolve while the domain still points at a different deployment from the tree you are editing. Ready is not current.

The original described this as the organism’s sense of its own body in public. That is a metaphor for a check, and the check is more modest than the metaphor: compare what the local source says is the latest published thing with what the public surfaces say, and refuse to proceed on a mismatch. A person still decides to deploy.

The repository records what happened around the original. A new homepage built in mid-June sat on a branch and was never merged, so deploys from the main line kept shipping the older one. On 2 July the live site was verified byte-identical to a working tree that had not been committed. On 3 July a commit pinned that exact state so that a rollback point existed. The timeline gives the dated steps and what each one shows about the problem the gate is for.

01

15 June 2026 · Built and not merged

A new homepage with a pulse console, a visitor pathfinder, an ecosystem map and bilingual boards is built on a branch. According to the 3 July merge message they were never merged, and each deploy from the main line since then kept shipping the older homepage.

02

1 July 2026 · The note is written

The original of this transmission records a comparison in which the local package was ahead of the public domain. That account is the note’s own record and is not restated here as a measurement.

03

2 July 2026 · Live matches an uncommitted tree

A later commit message states that the live site was verified byte-identical to the working tree on this day, and that the tree had not been committed: no rollback point existed.

04

3 July 2026 · A rollback point, then a merge

One commit pins exactly what production was serving. A second merge restores the lab-foundation work and records that production deploy is the owner’s gate.

05

14 July 2026 · A defect the checks could not see

Two unclosed style blocks from the 3 July merge broke the lower part of the stylesheet. The fix commit says responsive rules and subpage styles were lost in production, and that public addresses pointed at redirecting variants. The checker does not read stylesheets.

06

19 July 2026 · The root changes

A build step promotes the lab homepage to the root route of the site. The older console is kept at its own route.

07

8 November 2026 · The parity test

The site test suite pins the newest transmission as number 45 across the status, sitemap, discovery files, archive and homepage, with 459 passing tests at the baseline for this revision.

The principle that survives

Local proof is not live proof, and live proof is not source proof. A gate should compare them and report the difference. It should not decide which one is right.

02

Six terms the organism must keep separate

And what in the repository checks each one

The original defined six terms. They are worth keeping, because most publication failures come from treating two of them as one. The explorer below gives each term and says, for each, what in the repository actually looks at it today. Where the answer is "a person", that is stated.

03

What the checker actually checks

The original twelve points, one by one

The original listed twelve questions the protocol should ask before publishing. A read-only checker exists in the repository. It runs ten named checks locally, and in live mode it adds two more, for reachability and for the status contract. In local mode it reads local files and calls the local request handlers for status, search and grounding. In live mode it fetches the live status, sitemap, agent files, archive and homepage and compares them with the local registry.

The panel maps the twelve questions to the checker. "Script" means a named check covers it. "Partial" means it is covered in part. "Manual" means no script covers it and a person does it, or does not. The sorting shows that the original protocol was mostly real and mostly small, and that two of its twelve points were never automated.

04

How drift shows up, in the checker’s own words

A model using the real check names

The original named a set of failure labels. None of them is in the code. What the code has are named checks that pass or fail, and a short list of states for endpoints that fail closed. Mapping the cases to those names is more honest than keeping the labels.

The model runs the live-mode sequence. The left column is a green build: it passes whatever the domain serves. The right column is the checker. Two early failures stop the run and report only themselves. The others are evaluated together and listed. The checker never says "behind" or "ahead". It says which check failed. Working out the reason is a person’s job.
