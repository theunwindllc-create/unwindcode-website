What Brain Cell Architecture can grow, what stays quarantined, and where proof lives.

Before lifecycle visuals turn self-evolution into a story, the page names the growth boundary: signal, research packet, sandbox trial, approval, integration, and rollback. A candidate cell can be proposed; it cannot join the organism until proof says yes.

  1. 01 / Signal

    Turn repeated failure into a scoped cell brief.

    The architecture can notice when a prompt loop is no longer enough and convert the pattern into a bounded problem packet.

    Input
    Repeated failure, missing capability, domain need, operator context, and constraints.
    Output
    A scoped problem packet and candidate cell brief.
    Blocked claim
    No hidden self-modification, autonomous code execution, or unreviewed filesystem write.
    Proof route
    Follow the lifecycle map
  2. 02 / Research

    Research the cell before code earns attention.

    A generated class is not trusted because it sounds plausible. The research packet names assumptions, interfaces, tests, risk, and rollback first.

    Memory boundary
    Only reviewed failures, source context, public docs, and proof artifacts inform candidate design.
    Output
    A research packet with assumptions, sources, interfaces, tests, and rollback plan.
    Blocked claim
    No generated cell becomes trusted because it compiles or reads well.
    Proof route
    Read the cell swap protocol
  3. 03 / Sandbox

    Run the candidate as evidence, not authority.

    The sandbox can test fixtures, failure traces, dependency behavior, and repair attempts without granting host or production authority.

    Tool boundary
    No host command, money movement, deployment, public posting, wallet call, or production load.
    Output
    Test results, failure traces, risk note, diff intent, and proof packet.
    Blocked claim
    No external side effect or capability joining runtime on first pass.
    Proof route
    Inspect the runtime console
  4. 04 / Integration

    Integrate only after review can still say no.

    A passing cell remains replaceable. Approval, source control, documentation, memory summary, proof ledger, and rollback decide whether it joins.

    Approval boundary
    Human review, source-control history, proof packet, and rollback path approve or refuse integration.
    Output
    An integrated or refused cell with visible proof and a rollback route.
    Blocked claim
    No irreversible self-evolution, hidden memory write, authority expansion, or unreviewed autonomy.
    Proof route
    Inspect the authority gate
Cell lifecycle

A new capability stays quarantined until proof says it can join the organism.

Brain Cell Architecture makes neurogenesis inspectable: a failure or need becomes research, then a bounded candidate cell, then sandbox evidence, immune review, human approval, and only then integration.

Read cell proof Design a cell lane
01Problem signal

The organism detects a repeated failure, missing capability, or domain need that cannot be solved by prompting harder.

02Research packet

The domain, risks, tools, memory needs, authority limits, and proof requirements are written down before code exists.

03Candidate cell

A proposed cell is generated or implemented as inert source, scoped to one job and one authority boundary.

04Sandbox trial

The candidate runs in a sterile environment with tests, logs, dependency checks, and no default host authority.

05Immune review

Risk gates decide whether the cell can proceed, needs changes, should be refused, or must ask the creator.

06Integrated skill

Only approved, tested cells become part of the organism, with source control, rollback path, and public proof attached.

Research packet

New capability design

Signal
A repeated task failure shows the organism needs a specialized cell instead of another prompt.
Cell path
Research writes the domain, inputs, memory needs, dependencies, fallback, and one narrow job for the candidate.
Proof bar
The packet must include acceptance tests, risk notes, rollback path, and what evidence would prove the cell useful.
Authority boundary
The request can propose source shape, but no generated code is trusted, run, or integrated by default.
Sandbox packet

Repair a failing cell

Signal
A candidate cell fails tests, exceeds scope, or touches a dependency it was not allowed to use.
Cell path
The repair loop reads logs, narrows the patch, reruns the sterile trial, and keeps host authority unavailable.
Proof bar
The console preserves failed test evidence, the exact fix intent, passing output, and remaining uncertainty.
Authority boundary
Sandbox repair can change candidate code only inside the review lane; production files remain locked until approval.
Creator gate

Pause on risky authority

Signal
The cell wants to write files, spend money, post publicly, call a private tool, or broadcast a Web3 action.
Cell path
The immune layer freezes execution, explains the request, names the destination, and asks the creator for a narrow decision.
Proof bar
Approval evidence includes command intent, affected surface, risk class, human decision, and the refusal path.
Authority boundary
High-risk actions stay inert unless explicit human approval grants that exact action for that exact destination.
Proof packet

Integrate a passing skill

Signal
The candidate has passed tests, stayed in scope, and produced evidence that it improves the organism.
Cell path
Integration adds source-control review, documentation, rollback route, memory summary, and public proof link.
Proof bar
The release packet names tests, changed files, operating boundary, owner, status, and what still remains experimental.
Authority boundary
A passing cell can join the organism only as a bounded skill with review history, rollback, and observable proof.
