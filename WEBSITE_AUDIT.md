# UnwindCode.ai Website Audit

Last updated: 2026-06-06

## Backend/API Findings

- `api/subscribe.js` is the active same-origin Vercel endpoint for homepage email capture.
- The endpoint normalizes email addresses, rejects malformed input before storage, and writes to Supabase REST when `SUPABASE_SERVICE_ROLE_KEY` is configured.
- If service-role storage is not configured, the endpoint falls back to the existing Supabase Edge Function path.
- Public failure responses now avoid returning raw upstream storage details, reducing the risk of exposing provider errors, schema details, or secret-adjacent text to browsers.
- `POST /api/subscribe` now rejects browser requests from untrusted cross-site origins before storage. Production origins are allowed by default; preview/custom origins can be added with `SUBSCRIBE_ALLOWED_ORIGINS`.
- Subscribe origin validation no longer trusts reconstructed `Host` / `X-Forwarded-Proto` origins. Missing-origin requests with unreviewed host headers are rejected, and localhost origins are development-only unless explicitly configured in `SUBSCRIBE_ALLOWED_ORIGINS`.
- Optional `page_path` metadata is accepted only as a same-site path, stripped to its pathname, and rejected before storage when it looks like an external URL, protocol-relative URL, overlong value, non-string value, or control-character payload.
- `SUBSCRIBE_LOG_EVENTS=true` enables metadata-only operational logs for accepted, rejected, and failed subscriber attempts without logging email addresses, service keys, or upstream provider details.
- When `RATE_LIMIT_REST_URL`, `RATE_LIMIT_REST_TOKEN`, and `RATE_LIMIT_SALT` are configured, `POST /api/subscribe` performs a durable pre-storage rate-limit check using a salted hash key, not the raw client address or email.
- Durable subscribe rate-limit identity now hashes route plus a validated client address only. Forwarded client headers are ignored by default, `User-Agent` is not part of the primary quota bucket, and `RATE_LIMIT_TRUST_PROXY_HEADERS=true` is required before `cf-connecting-ip`, `x-real-ip`, or the first `x-forwarded-for` value can influence the key.
- In `VERCEL_ENV=production`, `POST /api/subscribe` fails closed with a generic `503` when durable rate-limit configuration is missing, the limiter is unavailable, or the configured limiter returns a non-2xx HTTP error, preventing storage from bypassing the abuse gate.
- In `VERCEL_ENV=production`, `POST /api/subscribe` now requires explicit upstream configuration before storage. Supabase URL must be configured, and either the service-role REST key or anon Edge Function key must be configured; missing upstream env returns a generic `503` after the durable limiter check and before any Supabase request.
- Successful `POST /api/subscribe` responses now return only operational status and destination metadata; they no longer echo the normalized subscriber email back to the browser.
- The browser now calls only same-origin `/api/subscribe` for homepage signup. Direct provider fallback coordinates and function paths are not shipped in `main.js`, so browser traffic stays behind the Vercel proxy, origin checks, metadata-only logging, and durable rate-limit hook.
- `api/chat.js` is the active same-origin Vercel governance proxy for homepage Brain chat submissions.
- `POST /api/chat` rejects untrusted browser origins, malformed messages, and malformed conversation IDs before forwarding prompt text to the Supabase Edge Function.
- Chat origin validation no longer trusts reconstructed `Host` / `X-Forwarded-Proto` origins. Missing-origin requests with unreviewed host headers are rejected, localhost origins are development-only unless explicitly configured in `CHAT_ALLOWED_ORIGINS`, and subscribe-only allowed origins no longer grant chat proxy access.
- `POST /api/chat` now rejects control-character message payloads before rate limiting, grounding checks, or upstream forwarding.
- When `RATE_LIMIT_REST_URL`, `RATE_LIMIT_REST_TOKEN`, and `RATE_LIMIT_SALT` are configured, `POST /api/chat` performs a durable pre-forward rate-limit check using a salted hash key, not the raw client address or prompt text.
- Durable chat rate-limit identity now shares the same explicit proxy-trust behavior as subscribe: forwarded client headers are ignored unless `RATE_LIMIT_TRUST_PROXY_HEADERS=true`, malformed forwarded values are discarded, and `User-Agent` rotation does not split the primary quota bucket.
- In `VERCEL_ENV=production`, `POST /api/chat` fails closed with a generic `503` when durable rate-limit configuration is missing, the limiter is unavailable, or the configured limiter returns a non-2xx HTTP error, preventing chat forwarding from bypassing the abuse gate.
- In `VERCEL_ENV=production`, `POST /api/chat` now requires explicit `SUPABASE_URL` and `SUPABASE_ANON_KEY` configuration before upstream forwarding. Missing upstream env returns a generic `503` after the durable limiter check and before any Supabase request.
- `POST /api/chat` now applies a server-side grounding gate for financial/Web3/live-deployment/autonomous-authority/wallet-signing, transaction-action, and selected future-vision/site-claim availability prompts before upstream chat forwarding. High-risk, future-vision, or qualification-required matches return `409` with `answer_generation: disabled`; risky-domain prompts without reviewed grounding also fail closed instead of requesting a bare upstream answer.
- Chat grounding `409` responses now embed the same public grounding packet schema used by `/api/grounding`, including `schema_version`, `mode`, `answer_policy`, citations, source citation indexes, required claim qualifications, refusal rules, review flags, and safety boundaries.
- Browser chat now treats `/api/chat` responses as terminal and no longer ships a direct provider fallback path, so grounding `409` and validation responses cannot bypass same-origin policy handling from the browser.
- Public chat failures now return generic proxy errors instead of provider details; `CHAT_LOG_EVENTS=true` enables metadata-only chat logs without logging prompt text, anon keys, or upstream response bodies.
- The browser now calls only same-origin `/api/chat`; direct provider chat fallback coordinates and function paths are not shipped in `main.js`.
- `public/robots.txt`, `public/sitemap.xml`, and `public/llms.txt` are active Vite public metadata files for live routes only. `robots.txt` points crawlers at the sitemap and asks crawlers to avoid `/api/` paths.
- `public/ai-services.json` is the active public AI-service metadata file. It lists only current public API surfaces (`/api/architecture`, `/api/assets`, `/api/chat`, `/api/claims`, `/api/grounding`, `/api/organisms`, `/api/search`, `/api/status`, `/api/subscribe`, `/api/transmissions`) with bounded claim scopes, public citations, source files, source routes, and safety boundaries.

- `public/data/assets.json` is the active public asset provenance registry. It records the Transmission 24 social carousel package with source file hashes, generated PNG file hashes, byte counts, alt text, rights notes, publication status, manual approval gates, machine-readable authority boundaries, and a public-safe approval record schema.
- Asset packages now expose a canonical `asset_package_sha256` derived from package identity, source file hashes, generated file hashes, approval schema version, and authority boundaries so future approval records and provenance attestations have a concrete digest target.
- The asset approval record schema defines required public fields for future reviewed publication/provenance approvals while keeping `approval_records` empty until a real reviewed approval exists.
- `api/assets.js` exposes the asset registry as a read-only Vercel API with list, single-package lookup, review-status filtering, publication-status filtering, validator-aware public cache headers, and write-method rejection.
- `/api/assets` successful public registry reads now use `Cache-Control: public, max-age=60, must-revalidate`, `ETag`, `Last-Modified`, and full-registry conditional `304` responses so approval-bearing asset metadata has a shorter freshness window and concrete cache validators.
- `/api/assets` now returns stable generic JSON failures with `Cache-Control: no-store` for malformed lookup values, unknown ids, write methods, and registry-loader failures, avoiding public caching of error states and preventing filesystem/parser details from reaching clients.
- `/api/assets` now uses the shared durable rate-limit hook before registry and metadata loading for valid asset registry reads. Limiter payloads contain salted route/client hashes only, `429` and limiter-unavailable responses are generic and `no-store`, and production fails closed when limiter configuration is missing or unavailable.
- `/api/assets` now fails closed with a generic non-cacheable error if future approval records reference a different asset package id or `asset_package_sha256`.
- `public/data/claims.json` is the active public claim/evidence registry. It labels homepage and financial/Web3 claims by claim status, evidence status, risk level, source files, public citations, and interpretation boundaries.
- `api/claims.js` exposes the claim registry as a read-only Vercel API with list, single-claim lookup, claim-status filtering, evidence-status filtering, category filtering, public cache headers, and write-method rejection.
- `/api/claims` now returns stable generic JSON failures with `Cache-Control: no-store` for malformed lookup values, unknown ids, write methods, and registry-loader failures, avoiding public caching of error states and preventing filesystem/parser details from reaching clients.
- `/api/claims` now uses the shared durable rate-limit hook before registry loading for valid claim registry reads. Limiter payloads contain salted route/client hashes only, `429` and limiter-unavailable responses are generic and `no-store`, and production fails closed when limiter configuration is missing or unavailable.
- `public/data/organisms.json` is the active public organism registry. It records capabilities, safety boundaries, memory model labels, live route references, source files, claim references, and public review status without credentials or runtime-only evidence.
- `api/organisms.js` exposes the registry as a read-only Vercel API with public cache headers, single-organism lookup by `id`, and write-method rejection.
- `/api/organisms` now returns stable generic JSON failures with `Cache-Control: no-store` for malformed lookup values, unknown ids, write methods, and registry-loader failures, avoiding public caching of error states and preventing filesystem/parser details from reaching clients.
- `/api/organisms` now uses the shared durable rate-limit hook before registry loading for valid public organism reads. Limiter payloads contain salted route/client hashes only, `429` and limiter-unavailable responses are generic and `no-store`, and production fails closed when limiter configuration is missing or unavailable.
- `public/data/transmissions.json` is the active public transmission registry. It covers every active published transmission with topic tags, memory layers, citations, confidence, source files, and public review status.
- `api/transmissions.js` exposes the transmission registry as a read-only Vercel API with list, single-transmission lookup, and topic filtering.
- `api/_shared/claim-context.js` is the canonical public claim-context helper for transmission enrichment. It owns inferred transmission claim references, deterministic matched-claim sorting, public claim qualifications, and sensitive-topic review flags for `web3-safety`, `financial-safety`, and `approval-gates`.
- Direct `/api/transmissions` responses now decorate public transmission entries with inferred `claim_references`, compact `claim_context`, and public-safe `claim_qualifications` from the shared claim-context helper when source routes/files overlap, so high-risk financial/Web3 entries carry qualification labels, interpretation boundaries, and citations before they are used as RAG seed metadata.
- Direct `/api/transmissions` claim context also marks sensitive `web3-safety`, `financial-safety`, and `approval-gates` topic tags with `requires_qualification: true` and a `sensitive_topic_requires_grounding` review flag even when no explicit claim row matches, preventing Web3/approval seed content from looking low-risk by omission.
- `/api/transmissions` now returns stable generic JSON failures with `Cache-Control: no-store` for malformed lookup values, unknown ids, write methods, and registry/claim-loader failures, avoiding public caching of error states and preventing filesystem/parser details from reaching clients.
- `/api/transmissions` now uses the shared durable rate-limit hook before registry and claim-context loading for valid public transmission reads. Limiter payloads contain salted route/client hashes only, `429` and limiter-unavailable responses are generic and `no-store`, and production fails closed when limiter configuration is missing or unavailable.
- `api/status.js` exposes a read-only public backend status endpoint built from public AI-service metadata and public architecture, asset, claim, organism, and transmission registries.

- `GET /api/status` now aggregates public operational controls from `public/ai-services.json`, including durable-rate-limited endpoints, production-fail-closed endpoints, answer-generation-disabled endpoints, same-origin guarded endpoints, and limiter payload boundaries without exposing live env configuration.
- `/api/status` now keeps success responses public-cacheable but returns `Cache-Control: no-store` on method and registry-loader failures. Its in-process status cache refreshes when public metadata source file signatures change.
- `api/search.js` exposes a read-only public registry search endpoint over architecture, asset, claim, organism, and transmission metadata.
- `GET /api/search` requires a bounded query or reviewed filter, returns citations/source files/review status/claim references, supports `type`, `claim_status`, `evidence_status`, and `risk_level` filters, and rejects write methods without reading private filesystem content.
- Search results now include deterministic lexical ranking, match scores, matched terms, compact public-safe snippets, and claim-context summaries so downstream RAG/chat layers can cite and qualify results before answer synthesis.
- Search results now preserve public `memory_layers` and `memory_context` for architecture, organism, and transmission entries, and support a bounded `memory_layer` filter without adding embeddings or answer synthesis.

## Current Safety Boundary

- Keep `SUPABASE_SERVICE_ROLE_KEY` server-side only.
- Keep public responses generic on storage failures.
- Keep `SUBSCRIBE_ALLOWED_ORIGINS` limited to deployed UnwindCode.ai domains and reviewed preview hosts. Do not rely on request `Host` / `X-Forwarded-Proto` reconstruction as an implicit allowed origin.
- Keep subscribe logs metadata-only; do not log submitted email addresses, service role keys, or upstream response bodies.
- Keep subscribe success responses identifier-free; do not return submitted or normalized email addresses to public clients after storage.
- Keep subscribe rate-limit checks durable and privacy-preserving: send salted hashes and route/window metadata only, never submitted emails, raw IPs, service keys, or upstream bodies. In production, missing, unavailable, or HTTP-error limiter checks should fail closed before storage.
- Keep subscribe upstream configuration explicit in production: require `SUPABASE_URL` and at least one reviewed storage credential path (`SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_SERVICE_KEY` for REST or `SUPABASE_ANON_KEY`/`VITE_SUPABASE_ANON_KEY` for Edge Function fallback). Do not let production storage use baked-in upstream defaults.
- Keep `RATE_LIMIT_TRUST_PROXY_HEADERS=false` unless the deployment proxy has been reviewed to overwrite or strip client-supplied `cf-connecting-ip`, `x-real-ip`, and `x-forwarded-for` headers. If enabled, only valid IP-shaped proxy header values may influence the limiter key.
- Keep chat logs metadata-only; do not log submitted prompt text, anon keys, conversation payloads, or upstream response bodies.
- Keep `CHAT_ALLOWED_ORIGINS` separate from subscribe-only preview origin config unless chat/RAG access for that preview host has been explicitly reviewed.
- Keep chat rate-limit checks durable and privacy-preserving: send salted hashes and route/window metadata only, never raw prompts, raw IPs, anon keys, or upstream bodies. In production, missing, unavailable, or HTTP-error limiter checks should fail closed before forwarding.
- Keep chat upstream configuration explicit in production: require `SUPABASE_URL`/`VITE_SUPABASE_URL` and `SUPABASE_ANON_KEY`/`VITE_SUPABASE_ANON_KEY` before forwarding. Do not let production chat use baked-in upstream defaults.
- Keep `User-Agent` out of the primary durable limiter identity so clients cannot split quotas by rotating browser strings.
- Keep chat grounding gates server-side for financial/Web3/live-deployment/autonomous-authority/wallet-signing prompts, transaction-action prompts such as swaps/fund transfers/transaction signing, and claim-bearing future-vision availability prompts; do not request upstream answers for risky or qualification-required prompts until citations, claim qualifications, and refusal rules can be rendered. Preserve the shared grounding packet shape in `409` responses without echoing submitted prompts.
- Keep browser submission flows behind same-origin serverless proxies only. Do not ship direct provider fallback coordinates, function paths, provider tokens, or baked-in upstream configuration in `main.js` or built browser assets.
- Keep `public/ai-services.json` limited to current public API endpoints, live source routes, public source files, bounded claim scopes, citations, and safety boundaries.
- Keep architecture registry entries source-backed to active public pages and transmissions, with claim references that match `public/data/claims.json`; do not include exact approval mechanics, deployment procedures, private notes, raw prompts, runtime evidence, or operational commands.
- Keep `/api/architecture` error responses non-cacheable and generic; do not expose registry parser errors, filesystem paths, stack traces, or public-cache headers on `4xx`/`5xx` responses.
- Keep asset registry entries source-backed to reviewed asset packages; include source-file hashes, generated-file hashes, byte counts, source files, alt text, rights notes, publication status, approval gates, authority boundaries, and public-safe approval record schemas without granting automated public posting authority.
- Keep `asset_package_sha256` bound to source hashes, generated hashes, approval schema version, and authority boundaries before future approvals or attestations reference the package.
- Keep asset approval records public-safe and role-based only. Do not include private approver identities, private notes, raw prompts, credentials, sensitive user data, wallet secret material, or sensitive on-chain data; leave `approval_records` empty unless a reviewed approval actually exists.
- Future asset approval records must match the package id and canonical package digest; mismatches should fail closed before public API responses or search retrieval.
- Keep `/api/assets` success responses validator-aware with a short revalidation window while asset packages carry approval or publication state.
- Keep `/api/assets` behind durable rate limiting before registry loading for valid public asset requests. Limiter calls must use salted route/client hashes only and must not include asset ids, filters, source file paths, generated asset paths, registry contents, or raw client addresses.

- Keep claim registry entries source-backed to active public pages and transmissions; include claim/evidence status, risk labels, public citations, and interpretation boundaries before broad RAG answers. Do not turn high-risk Web3 or financial language into wallet authority, current deployment proof, or unqualified automation claims.
- Keep `/api/claims` behind durable rate limiting before registry loading for valid public claim requests. Limiter calls must use salted route/client hashes only and must not include claim ids, filters, claim labels, citations, source file paths, registry contents, or raw client addresses.
- Keep `/api/claims` error responses non-cacheable and generic; do not expose registry parser errors, filesystem paths, stack traces, or public-cache headers on `4xx`/`5xx` responses.
- Keep organism registry entries source-backed to active public files, with claim references that match `public/data/claims.json`; do not include private repositories, unreleased routes, runtime evidence, credentials, or hidden operational procedures.
